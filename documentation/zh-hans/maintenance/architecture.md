## Gnosis 包结构完整展开（含子模块与设计理由）

---

### 1. Gnosis.Core

**职责**：提供所有其他包共享的基础设施，零外部依赖，纯 C# 实现。

| 子模块 | 职责 | 设计理由 |
|:---|:---|:---|
| `Math` | 向量、矩阵、四元数、几何图元、随机数、噪声 | 游戏开发的数学基础，必须自研以确保跨平台确定性与性能 |
| `Collection` | 稀疏集、对象池、环形缓冲、位数组、自定义分配器容器 | ECS 与渲染系统的内存布局基础，标准库容器无法满足 SIMD 对齐等需求 |
| `Event` | 信号槽、委托、事件总线 | 松耦合通信的基础设施，零分配设计 |
| `Thread` | 任务调度器、线程池、原子操作、无锁队列 | 多核利用的基础，需要平台无关的统一抽象 |
| `IO` | 同步/异步文件读写、内存映射、虚拟文件流 | 跨平台文件系统抽象，支持热重载与资产流式加载 |
| `Memory` | 分配器接口、堆分配器、栈分配器、池分配器、内存跟踪 | 游戏开发对内存分配有极致控制需求，必须提供可替换的分配器体系 |
| `Hash` | xxHash、MurmurHash、CRC32、SHA256 | 资产 GUID、校验和、网络同步都需要高性能哈希 |
| `Time` | 时间缩放、计时器、帧时间平滑、日期时间工具 | 动画、物理、协程都需要统一的时间基准 |
| `Platform` | 平台检测、系统信息、动态库加载、原子文件操作 | 屏蔽操作系统差异，提供统一的平台服务接口 |
| `Config` | `IConfigProvider` 接口、配置变更监听 | 定义配置抽象的契约，不依赖具体实现（GON/远程） |
| `String` | 字符串视图、字符串池、编码转换 | 减少字符串分配，提升 UI 与序列化性能 |
| `Diagnostic` | 断言、日志接口、错误码体系 | 跨包的诊断基础设施，不依赖具体的日志实现 |

### 2. Gnosis.IR

**职责**：自研中间表示，用于 gg 字节码优化与着色器编译，避免 ONNX/MLIR 的循环依赖问题。

| 子模块 | 职责 | 设计理由 |
|:---|:---|:---|
| `Graph` | 基本块、控制流图、数据流图、SSA 形式构建 | IR 的核心数据结构，所有优化 Pass 的基础 |
| `Instruction` | IR 指令集定义（算术、分支、内存、向量、原子） | 统一的指令抽象，可同时服务于字节码与着色器 |
| `Analysis` | 支配树、循环检测、活跃变量分析、别名分析 | 优化 Pass 依赖的分析工具集 |
| `Transform` | 常量折叠、死代码消除、内联、循环展开、向量化 | 平台无关的优化 Pass 集合 |
| `Lowering` | 从 AST 到 IR 的 lowering 规则 | 将 gg 脚本 AST 转换为 IR 的规范流程 |
| `Emitter` | 字节码发射器、SPIR-V 发射器、文本 IR 输出 | 将优化后的 IR 转换为目标格式 |
| `Validation` | IR 验证器、类型检查、SSA 完整性检查 | 确保 IR 转换与优化过程的正确性 |

---

### 3. Gnosis.Runtime

**职责**：托管 gg 字节码的虚拟机，提供协程、热重载等运行时服务。

| 子模块 | 职责 | 设计理由 |
|:---|:---|:---|
| `VM` | 字节码解释器、栈帧管理、指令分发 | gg 脚本的执行引擎核心 |
| `Interop` | C# 原生函数绑定、值类型转换、异常桥接 | gg 与宿主语言的双向调用通道 |
| `Coroutine` | 协程状态机、调度器、`YieldInstruction` 体系 | 异步逻辑的轻量级实现，依赖 VM 的栈保存能力 |
| `HotReload` | 代码热重载、状态迁移、元数据比对 | 开发效率的关键，需要 VM 层面的深度支持 |
| `Reflection` | gg 类型系统运行时表示、动态调用 | 支持脚本间的动态类型交互 |
| `Debug` | 断点、单步执行、变量监视接口 | 为编辑器和调试工具提供运行时钩子 |
| `Sandbox` | 脚本权限控制、资源配额、安全隔离 | 支持 Mod 和用户生成内容的执行安全 |

### 4. Gnosis.ECS

**职责**：实体组件系统，高性能游戏逻辑的组织框架。

| 子模块 | 职责 | 设计理由 |
|:---|:---|:---|
| `Entity` | 实体 ID 分配、代际管理、实体查询 | 实体生命周期的核心管理 |
| `Component` | 组件类型注册、组件存储、组件反射 | 类型安全的组件管理，支持脚本动态访问 |
| `Archetype` | 原型（Archetype）存储、分块（Chunk）内存布局 | 缓存友好的组件存储策略，SIMD 迭代的基础 |
| `System` | 系统调度、依赖图构建、并行执行 | 逻辑组织的核心，支持自动并行化 |
| `Query` | 实体查询迭代器、变更过滤、排序 | 高效遍历实体的 API 层 |
| `World` | 世界容器、子世界、世界序列化 | 支持多场景、多宇宙隔离 |
| `Command` | 延迟命令缓冲（实体创建/销毁/组件修改） | 避免在系统迭代中直接修改世界造成数据竞争 |
| `Observer` | 组件变更观察、事件触发 | 响应式逻辑的基础，替代轮询 |

### 5. Gnosis.Asset

**职责**：资产导入、处理、缓存与打包的全生命周期管理。

| 子模块 | 职责 | 设计理由 |
|:---|:---|:---|
| `VFS` | 虚拟文件系统、挂载点管理、路径解析 | 统一资产访问，支持多来源（磁盘/包/网络） |
| `Format` | gg-object、glTF、FBX、PNG 等格式解析器 | 资产导入的源头，需要可扩展的解析器体系 |
| `Import` | 导入器框架、依赖收集、资产版本检测 | 将原始文件转换为引擎内部格式的标准化流程 |
| `Process` | 资产处理器（纹理压缩、网格优化、音频转码） | 平台特化的资产优化步骤 |
| `Meta` | GUID 生成与解析、依赖图、资产哈希、缩略图 | 资产引用与增量构建的核心元数据 |
| `Cache` | 构建结果缓存、增量构建决策 | 加速迭代，避免重复处理未变更资产 |
| `Bundle` | 资产包打包、压缩、加密、分块加载索引 | 运行时资产分发的载体 |
| `Reference` | 资产引用计数、强弱引用、延迟加载 | 资产生命周期管理，防止内存泄漏 |

### 8. Gnosis.Database

**职责**：嵌入式 NoSQL 引擎，不仅服务于游戏存档，亦可独立使用。

| 子模块 | 职责 | 设计理由 |
|:---|:---|:---|
| `Engine` | 存储引擎（LSM 树 / B+ 树）、页面管理 | 持久化存储的核心数据结构 |
| `WAL` | 预写日志、崩溃恢复 | 事务持久性的保证 |
| `Transaction` | ACID 事务、快照隔离 | 并发控制与数据一致性 |
| `Query` | 查询接口、范围扫描、前缀查询 | 键值存储的数据访问层 |
| `Index` | 二级索引、复合索引 | 加速非主键查询 |
| `Compaction` | 压缩策略、垃圾回收 | 存储空间回收与读取性能优化 |
| `Cache` | 页缓存、行缓存 | 降低磁盘 I/O 的缓冲层 |

## Gnosis 架构团队指南：避免致命混淆

### 一、三层蛋糕模型（必须牢记）

这是理解整个 Gnosis 生态的基石。混淆这三层将导致设计决策的全面偏差。

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                          Layer 3: 游戏内容层                                   │
│  ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐    │
│  │  Game   │ │  Mod    │ │  DLC    │ │ Plugin  │ │ Editor  │ │ Server  │    │
│  │ (gg)    │ │ (gg)    │ │ (gg)    │ │ (gg)    │ │ (gg)    │ │ (gg)    │    │
│  └─────────┘ └─────────┘ └─────────┘ └─────────┘ └─────────┘ └─────────┘    │
│                                                                              │
│  编写语言: gg-script (以及 gg-shader, gg-widget, gg-neural)                   │
│  责任方: 游戏开发者 / 模组作者 / 第三方工具开发者                               │
└─────────────────────────────────────────────────────────────────────────────┘
                                       ↑
                              (通过 Gnosis 框架层通信)
                                       ↑
┌─────────────────────────────────────────────────────────────────────────────┐
│                          Layer 2: 游戏引擎层 (官方范例)                         │
│                                                                              │
│  一个具体的、基于 Gnosis 元引擎构建的、可独立运行的 C# 应用程序。                  │
│  它包含: 编辑器界面、资产导入器、构建管线、项目模板、启动器。                       │
│                                                                              │
│  编写语言: C# (调用 Gnosis 包)                                                 │
│  责任方: Gnosis 官方团队 (提供范例实现)                                         │
└─────────────────────────────────────────────────────────────────────────────┘
                                       ↑
                              (通过直接 API 调用使用)
                                       ↑
┌─────────────────────────────────────────────────────────────────────────────┐
│                          Layer 1: Gnosis 元引擎层                              │
│                                                                              │
│  25 个 C# 包构成的基础设施。它本身不可运行，必须由游戏引擎层实例化。                │
│  它提供虚拟机、渲染 RHI、ECS、资产管线等能力。                                   │
│                                                                              │
│  编写语言: C# (零外部依赖)                                                      │
│  责任方: Gnosis 核心团队                                                       │
└─────────────────────────────────────────────────────────────────────────────┘
```

**致命错误示例**：

- ❌ 在 `Gnosis.Core` 中写游戏逻辑 → **游戏逻辑属于 Layer 3，用 gg-script 写**
- ❌ 在 `gg-script` 中实现渲染管线 → **渲染管线属于 Layer 1/2，用 C# 写**
- ❌ 认为 Gnosis 包可以直接 Build 出一个游戏 → **必须先构建一个游戏引擎，再用游戏引擎构建游戏项目**

---

### 二、两个 UI 系统的绝对边界：Widget vs GameUI

| 特征 | `Gnosis.Widget` | `Gnosis.GameUI` |
|:---|:---|:---|
| **目标用户** | 引擎开发者、工具开发者 | 游戏开发者、玩家 |
| **运行环境** | 编辑器进程（C# 宿主） | 游戏运行时（gg-script 脚本） |
| **渲染模式** | 保留模式（Retained Mode） | 即时模式为主（Immediate Mode）或混合 |
| **典型控件** | 属性面板、资产浏览器、曲线编辑器 | 血条、技能图标、对话框、背包格 |
| **数据绑定** | `gg-widget` 语法，双向绑定 | `gg-script` 直接操作 UI 组件 |
| **性能目标** | 低刷新率（30fps 足够），高数据密度 | 高刷新率（60fps+），低延迟交互 |
| **依赖关系** | 不依赖 ECS | 依赖 ECS（通过 UI 组件与系统） |

**致命错误示例**：

- ❌ 在游戏中使用 `Gnosis.Widget` 画血条 → **导致性能灾难，且无法与 gg-script 交互**
- ❌ 在编辑器工具中硬编码 `Gnosis.GameUI` 控件 → **失去保留模式的布局优势，开发效率低下**

---

### 三、命名规范铁律

| 规则 | 正确示例 | 错误示例 | 说明 |
|:---|:---|:---|:---|
| 包名使用**单数名词** | `Gnosis.Asset` | `Gnosis.Assets` | 表示一个资产系统，而非多个资产 |
| 子模块不使用主包名 | `Graphic.FX` | `Graphic.Core` | `Core` 是顶级包名，禁止嵌套使用 |
| 避免动词或 -ing 形式 | `Animation.Tween` | `Animation.Tweening` | `Tween` 是名词 |
| 适配器模式命名后缀 | `Animation.Adapter` | `Animation.SpinePlugin` | 后缀统一为 `Adapter` / `Provider` / `Driver` |

---

### 四、扩展点模式：Adapter / Provider / Driver

Gnosis 不内置 Live2D、Spine、Wwise 等第三方闭源 SDK 的运行时，但提供标准扩展接口。团队在命名和实现时必须遵循以下约定：

| 后缀 | 使用场景 | 示例 |
|:---|:---|:---|
| `Adapter` | 用于将第三方数据格式或运行时接入现有系统 | `Animation.Adapter` (Spine/Live2D) |
| `Provider` | 用于提供数据存储或配置的后端实现 | `Storage.Provider` (JSON/SQLite) |
| `Driver` | 用于硬件或底层库的抽象驱动 | `Audio.Driver` (OpenAL/WAAPI) |

**致命错误示例**：

- ❌ 直接在 `Gnosis.Animation` 包中写 `SpineRuntime` 类 → **污染核心包，违反开源许可，应放在官方范例引擎或第三方插件中**

### 五、C# 与 gg-script 的职责边界

| 语言 | 适合编写的代码 | 不适合编写的代码 |
|:---|:---|:---|
| **C#** | 渲染管线、物理引擎、内存分配器、编译器、工具链 | 角色技能逻辑、任务流程、UI 交互、数值配置 |
| **gg-script** | 游戏玩法逻辑、AI 行为、UI 响应、数据驱动内容 | 底层数学库、多线程调度、文件解析、硬件抽象 |

---

### 六、包依赖方向检查清单

在添加新包或修改依赖时，请回答以下问题：

1. 这个包是否**必须**依赖另一个包？能否通过接口解耦？
2. 依赖方向是否与架构层级一致？**基础层 ← 核心层 ← 子系统层**，绝不允许反向依赖。
3. 是否引入了**循环依赖**？运行 `dotnet sln` 分析器检查。
4. 这个包将来是否会被**可选地替换**？如果是，请引入 `Provider` / `Adapter` 接口。

---

### 七、常见问题速查

| 问题 | 答案 |
|:---|:---|
| 我想加一个新的渲染特性，应该放在哪个包？ | `Gnosis.Graphic` 下的相应子模块，或在 `FX` / `Character` 下新建。 |
| 我想接入 Live2D，怎么做？ | 在 `Gnosis.Animation.Adapter` 命名空间下定义接口，由官方范例引擎或第三方插件实现具体逻辑，游戏层通过 gg-script 调用统一接口。 |
| 为什么 `Gnosis.Database` 在核心层而 `Storage` 也在？ | `Database` 是通用嵌入式 NoSQL 引擎，`Storage` 是面向存档/玩家偏好的封装，它**可选地**使用 `Database` 作为后端。 |
| `Gnosis.Plugin` 管理的是 C# 插件还是 gg 插件？ | 两者皆可。它管理的是运行时的代码与资产包，无论其内部是 C# 还是 gg 字节码。对于 gg 脚本插件，它负责加载字节码并创建隔离的 VM 上下文。 |
| 编辑器是用 C# 写的，为什么有 `Gnosis.Widget`？ | 编辑器是 C# 应用程序，但它需要 UI 框架。`Widget` 就是用 C# 实现的、为工具链服务的 UI 库，并可通过 `gg-widget` 声明式描述界面。 |
